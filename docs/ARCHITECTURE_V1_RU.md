# ProtoOS v1.3 — архитектура и реализация

Нормативная база: замороженная спецификация v1.0 ([`TECHNICAL_SPECIFICATION_RU.md`](../TECHNICAL_SPECIFICATION_RU.md)) и решения 01–19 ([`DECISION_REGISTER_RU.md`](../DECISION_REGISTER_RU.md)). Расширения v1.1 (`write`, `sleep`, демо-режим) описаны в [`SPEC_V1_1.md`](SPEC_V1_1.md), расширения v1.2 (ввод с консоли через PLIC, `read`, `uptime`, `procinfo`, оболочка) — в [`SPEC_V1_2.md`](SPEC_V1_2.md), расширения v1.3 (распределитель страниц, 8 слотов процессов, `spawn`/`kill`/`meminfo`/`slotinfo`, встроенные программы) и исправления v1.3.1 — в [`SPEC_V1_3.md`](SPEC_V1_3.md). Этот документ фиксирует технические решения, которые спецификации оставляют исполнителю. English version: [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Платформа
QEMU `virt`, `-cpu rv64 -smp 1 -m 128M`; OpenSBI `fw_dynamic.bin` работает в M-mode и передаёт управление ядру в S-mode по адресу `0x80200000` (`a0` = номер hart, `a1` = дерево устройств). ISA ядра и пользователя: RV64IM + Zicsr + Zifencei, LP64, без плавающей точки. В U-mode `sstatus.FS = VS = Off`, поэтому любая FP/vector-инструкция вызывает исключение illegal instruction и процесс помечается FAULTED (FP-состояние не хранится).

## Порядок загрузки
1. `_start` (`boot.S`): прерывания выключены, `sscratch = 0`, обнуление `.bss` и пользовательских страниц, установка `stvec`.
2. `kernel_main` (`kernel.c`): проверка hart 0 и `satp = 0`, разбор дерева устройств (адрес UART, timebase, `bootargs` из `/chosen`), выбор сценария.
3. Настройка пула страниц ниже дерева устройств (`mem.c`), построение корней Sv39 ядра, шаблона, A и B (`vm.c`), переключение на корень ядра, проверка, что `satp` принят.
4. Создание процессов A и B, включение прерывания приёма UART в самом UART и в PLIC (`input.c`), запуск таймера, установка `sie.STIE` и `sie.SEIE`, вход в первый процесс через `sret` (`proc.c`, `trap.S`).

## Физическая память (статическая)
| Диапазон | Содержимое | Отображение |
|---|---|---|
| `0x80000000`–`0x801FFFFF` | OpenSBI | недоступен из S/U (PMP) |
| `__kernel_start` … `__text_end` | код ядра | все корни: R X, U=0 |
| … `__rodata_end` | данные только для чтения (в т.ч. `kernel_secret` для теста N2) | R, U=0 |
| `kernel_stack_guard` (4 KiB) | страница под стеком ядра | **не отображается** |
| … `__kernel_end` | data/bss: стек ядра (16 KiB), аварийный стек, таблицы страниц, `procs` | R W, U=0 |
| `__user_a_text`, `__user_b_text` | по одной странице кода A и B | только в корне владельца, U=1 |
| `__user_prog_text` (3 страницы, v1.3) | общие встроенные программы и оболочка | каждый корень процесса по `0x4000000`, R X U |
| `user_{a,b}_{data,stack}` | страницы данных и стека A и B | только в корне владельца, U=1 |
| `0x80400000` — граница 2 MiB ниже дерева устройств (v1.3) | пул страниц: таблицы, страницы данных и стека процессов, созданных во время работы | все корни: листы 2 MiB R W, U=0; плюс пользовательские отображения 4 KiB у владельца |
| `0x10000000` | UART 16550 | R W, U=0 |
| `0x0C000000`, `0x0C002000`, `0x0C201000` | PLIC: приоритеты, разрешения S-mode, порог/claim S-mode (v1.2) | R W, U=0 |

Статические пользовательские страницы лежат за `__kernel_end` и **не входят** в тождественное отображение ядра: ни ядро, ни другой процесс их не видят. Весь образ должен помещаться ниже `0x80400000` (проверяется при компоновке).

## Распределитель страниц (v1.3)
`mem.c` управляет пулом `[0x80400000, end)`, где `end` — граница 2 MiB ниже дерева устройств (31 232 страницы на QEMU `virt` со 128 MiB), с помощью битовой карты; `mem_alloc` берёт самую младшую свободную страницу и **обнуляет её**, `mem_free` вызывает панику ядра на странице, которая не выделена. Выбор самой младшей страницы делает повторное использование освобождённых страниц детерминированным — на этом построен тест T13, который показывает, что повторно выданная страница приходит обнулённой.

## Виртуальная память
Корни Sv39 (`vm.c`): ядро, шаблон (ядро + страницы программ, никогда не устанавливается), A, B и по одному на каждый процесс, созданный во время работы; пользовательские листы 4 KiB; биты A/D выставляются программно (на Svadu не полагаемся). Везде ASID 0: каждая смена `satp` обрамлена `sfence.vma zero, zero`. Каждый корень также отображает пул страниц листами 2 MiB с U=0, чтобы ядро могло строить и очищать страницы любого процесса при любом установленном корне.

| VA процесса | A (слот 0) | B (слот 1) | слот *s* = 2…7 (во время работы) | Права |
|---|---|---|---|---|
| text | `0x400000` | `0x800000` | не отображается | R X U |
| data | `0x401000` | `0x801000` | `0x400000·(s+1) + 0x1000` | R W U |
| guard | `0x402000` | `0x802000` | `+ 0x2000` | не отображается |
| stack | `0x403000` (sp = `0x404000`) | `0x803000` (sp = `0x804000`) | `+ 0x3000` (sp = `+ 0x4000`) | R W U |
| программы | `0x4000000`–`0x4002FFF` | то же | то же | R X U (общие, только чтение) |

Непересекающиеся диапазоны VA приводят к тому, что обращение к чужому процессу указывает на адрес, который в корне нарушителя просто не отображён. Корень процесса, созданного во время работы, собирает `vm_create` из 5 страниц пула: корень и нижняя таблица уровня 1 начинаются как копии шаблона (общие с ним верхняя таблица уровня 1 ядра и таблицы уровня 0 для UART, PLIC и программ), затем одна собственная таблица уровня 0 отображает страницы данных и стека. `vm_destroy` освобождает ровно эти 5 страниц.

## Ловушки
Один вектор, `trap_entry` (`trap.S`). Протокол `sscratch`: пока процесс работает в U-mode, там лежит адрес `struct trap_frame` этого процесса; пока работает ядро — 0. Ядро никогда не включает `sstatus.SIE`, поэтому ловушка при `sscratch == 0` — это синхронное исключение S-mode: переход на аварийный стек и сообщение `KERNEL_PANIC` с `scause`/`sepc`/`stval` — в том числе при переполнении стека ядра в страницу-ограждение. При входе из U-mode сохраняются x1–x31, а также `sepc`, `sstatus`, `scause`, `stval` (288 байт), и работа продолжается на пустом стеке ядра; `user_return` восстанавливает кадр и выполняет `sret`.

Прерывания из U-mode: таймер S-mode (cause 5) вытесняет процесс; внешнее прерывание S-mode (cause 9, v1.2) — это прерывание приёма UART, доставленное через PLIC: ядро выполняет claim, переносит все принятые байты в кольцевой буфер на 128 байт (при заполнении новые байты отбрасываются), завершает claim и возвращается в прерванный процесс. Поскольку ядро никогда не включает `sstatus.SIE`, прерывание, возникшее во время работы ядра, принимается сразу после следующего `sret` либо замечается опросом `sip.SEIP`, пока ядро ждёт.

## Планировщик
Round Robin по 8 слотам процессов (v1.3; A и B в слотах 0 и 1) с квантом 10 мс (`timebase / 100`; 100 000 тиков на QEMU `virt`), который отсчитывает таймер S-mode через SBI TIME (`sbi_set_timer`). Выбор следующего процесса и переключение контекста выполняет ядро. Поиск следующего процесса начинается со слота после последнего запущенного, даже если этот процесс только что завершился (v1.3.1: позиция хранится в `sched.last_slot`). Процесс, созданный во время работы, при завершении, сбое или принудительном завершении сразу возвращает все свои страницы (`reclaim`); если установлен его корень, ядро сначала переключается на собственный корень. Номера процессов (pid) растут с 3 и никогда не используются повторно: когда номера исчерпаны, `spawn` возвращает −11 (v1.3.1).

Состояния: READY, RUNNING, SLEEPING, BLOCKED (v1.2: ожидание ввода), EXITED, FAULTED. В каждой точке планирования ядро сначала переводит в READY процессы SLEEPING, у которых наступило время пробуждения, и заблокированных читателей (BLOCKED), если в буфере есть ввод. Читатель запускается только при наличии ввода: `sched_dispatch` устанавливает его корень, затем копирует байты в его буфер и записывает результат в его `a0`. Если READY-процессов нет, но есть SLEEPING или BLOCKED, `sched_wait` ставит таймер на ближайшее пробуждение (или выключает его) и ждёт в `wfi` (при `sstatus.SIE` = 0, поэтому ловушка не возникает), обслуживая ожидающее внешнее прерывание опросом и выходя раньше, если пришёл ввод для заблокированного читателя; после этого планирование продолжается с новым квантом. Только когда нет ни одного процесса в состоянии READY, RUNNING, SLEEPING или BLOCKED, `sched_idle` выключает таймер, обнуляет `sie`, устанавливает корень ядра и останавливается в цикле `wfi` в `halt()`; контекст процесса больше никогда не загружается.

## Системные вызовы
`ecall` из U-mode; номер в `a7`, аргументы в `a0`–`a2`, результат в `a0`; выполнение продолжается с `sepc + 4`. Номера взяты из таблицы RISC-V Linux, кроме собственных вызовов ProtoOS (1001 и выше).

| Вызов | `a7` | Поведение |
|---|---|---|
| `read(fd, buf, len)` | 63 | v1.2: `fd` должен быть 0, `len` ≤ 256; каждый байт буфера должен лежать в действительной странице вызывающего с U+R+W **до того**, как вызов сможет заблокироваться; сразу возвращает имеющиеся в буфере байты (≥ 1), иначе процесс становится BLOCKED до прихода ввода; `len = 0` возвращает 0. Ошибки: −9, −14, −22 |
| `write(fd, buf, len)` | 64 | v1.1: `fd` должен быть 1, `len` ≤ 256; ядро обходит собственную таблицу страниц вызывающего и требует, чтобы каждый байт буфера лежал в действительной странице с U+R, **до того** как читать его с установленным `sstatus.SUM`; затем копирует в UART (непечатаемые байты, кроме `\n`, `\t` и, начиная с v1.2, backspace, заменяются на `?`). Ошибки: −9 неверный fd, −14 неверный адрес, −22 неверная длина |
| `sleep(ms)` | 1001 | v1.1: `ms` ≤ 60 000 (иначе −22); процесс находится в состоянии SLEEPING не меньше `ms` миллисекунд; `0` работает как `yield`; возвращает 0 |
| `uptime()` | 1002 | v1.2: микросекунды по `time` с момента входа в ядро |
| `procinfo(pid, buf)` | 1003 | v1.2: записывает состояние, число вытеснений, системных вызовов и запусков процесса `pid` (с v1.3 — любого pid, у которого есть слот, иначе −22) четырьмя словами в 32 байта памяти вызывающего с U+R+W (иначе −14); возвращает 0 |
| `spawn(program)` | 1004 | v1.3: запускает встроенную программу 1–5 в самом младшем свободном слоте; возвращает её pid. Ошибки: −22 неизвестная программа, −11 нет свободного слота (или исчерпаны pid, v1.3.1), −12 нет памяти |
| `kill(pid)` | 1005 | v1.3: завершает живой процесс, созданный во время работы (код выхода 137), его страницы возвращаются; 0. Ошибки: −3 нет такого живого процесса, −1 сам вызывающий или процесс, созданный при загрузке |
| `meminfo()` | 1006 | v1.3: свободные страницы в `a0`, всего страниц пула в `a1` |
| `slotinfo(slot, buf)` | 1007 | v1.3: pid, состояние, программа, вытеснения, системные вызовы, страницы слота 0–7 шестью словами в 48 байт памяти с U+R+W; 0. Ошибки: −22, −14 |
| `exit(code)` | 93 | процесс становится EXITED и больше никогда не запускается; страницы процесса, созданного во время работы, возвращаются сразу |
| `yield()` | 124 | процесс становится READY, планировщик переключается; возвращает 0 |
| `getpid()` | 172 | возвращает pid: 1 для A, 2 для B, с 3 и выше для процессов, созданных во время работы |
| любой другой | — | возвращает `-38` (ENOSYS); процесс продолжает работу |

Любое другое синхронное исключение из U-mode (page fault или access fault, illegal instruction, невыровненный доступ, breakpoint) помечает FAULTED только этот процесс (процесс, созданный во время работы, ещё и возвращает свои страницы); остальные продолжают работу.

## Один образ, много сценариев
Сценарий выбирается только через `bootargs` (`/chosen` в дереве устройств); ELF одинаков для всех.

| `bootargs` | A | B | Назначение |
|---|---|---|---|
| `protoos.mode=normal` | worker | worker | обычный режим, T7 |

| `protoos.mode=shell` | оболочка `proto>`: `help`, `ps`, `uptime`, `echo`, `attack`, а с v1.3 — `run`, `kill`, `mem` | worker | интерактивный режим, T12, T17 |
| `protoos.test=mem` / `spawn` / `kill` / `multi` / `spawn-bad` | `memcheck` дважды / один worker / kill и повторный запуск / три worker и crash / отклонённые вызовы и 200 циклов | worker | T13 / T14 / T15 / T16 / N9 |
| `protoos.test=read` / `read-bad` / `read-flood` | правильный / отклонённый / переполненный `read` | worker | T10 / N7 / N8 |
| `protoos.test=uptime` | `uptime` до и после `sleep(100)` | worker | T11 |

| `protoos.test=umode` / `preempt` | worker | worker | T2 / T3 |
| `protoos.test=getpid` / `yield` / `exit` | … | … | T4 |

`worker` — бесконечный цикл без системных вызовов, который на каждой итерации проверяет собственный контекст (`s0 + s1 == 0`, в `s2`–`s10` фиксированный шаблон) и заполняет контрольную область (canary) размером 2 KiB, так что потерянный или чужой контекст регистров обнаруживает сам процесс.
